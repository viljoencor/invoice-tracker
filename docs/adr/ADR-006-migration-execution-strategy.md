# ADR-006: Migration Execution Strategy

## Status

Accepted

## Context

Alembic migration `8cf5269df348` ("latest") was auto-generated by `alembic revision
--autogenerate` while the schema was already up to date, so both its `upgrade()`
and `downgrade()` functions are empty no-ops. A later migration
(`a1b2c3d4e5f6_add_refresh_tokens`) was created with
`down_revision = "8cf5269df348"`, so the no-op revision is now a permanent link in
the migration chain.

## Decision

We keep the empty migration in place rather than deleting it or squashing the
history:

- Alembic identifies revisions by their `revision`/`down_revision` IDs, not by
  file position. Deleting `8cf5269df348` would break every migration that
  descends from it (`a1b2c3d4e5f6`, `c3d4e5f6a7b8`, and this ADR's own
  `d4e5f6a7b8c9`), because Alembic would no longer be able to resolve the chain
  from `b6c2545a61ef` (init) to `head`.
- Any environment that has already run `alembic upgrade head` against the empty
  revision has a row for it in its `alembic_version` history. Removing the file
  would make that environment's history unresolvable without manually editing
  the `alembic_version` table.
- Squashing it into a neighboring migration would rewrite history that may
  already be applied in staging/production databases, which is unsafe for the
  same reason.

The `integration` CI job verifies `alembic downgrade -1` followed by
`alembic upgrade head` on every push specifically to catch this class of
migration-chain breakage before it reaches a real environment.

## Consequences

- The migration chain contains one revision that does nothing. This is
  intentional and documented (in the file's own docstring) so a future
  contributor doesn't "clean it up" and break the chain.
- New migrations should always set `down_revision` to the current head
  (`d4e5f6a7b8c9` as of this ADR) rather than trying to insert before or
  around the no-op revision.
